⏺ 是的，wg_queue_enqueue_per_device_and_peer 是异步的。

  从实现可以看出（queueing.h:165-186）：

  static inline int wg_queue_enqueue_per_device_and_peer(
      struct crypt_queue *device_queue, struct prev_queue *peer_queue,
      struct sk_buff *skb, struct workqueue_struct *wq, int *next_cpu)
  {
      // 1. 将包加入 peer 队列
      if (unlikely(!wg_prev_queue_enqueue(peer_queue, skb)))
          return -ENOSPC;

      // 2. 将包加入 device 队列
      cpu = wg_cpumask_next_online(next_cpu);
      if (unlikely(ptr_ring_produce_bh(&device_queue->ring, skb)))
          return -EPIPE;

      // 3. 异步调度工作队列处理（关键！）
      queue_work_on(cpu, wq, &per_cpu_ptr(device_queue->worker, cpu)->work);
      return 0;
  }

  异步机制：

  1. 入队操作同步 - 将数据包放入两个队列（peer 队列和 device 队列）是同步的
  2. 处理操作异步 - 通过 queue_work_on() 将实际处理工作提交到内核工作队列（workqueue）
  3. 立即返回 - 函数入队后立即返回，不等待数据包被处理

  工作流程：
  调用者 → enqueue → 入队成功 → 立即返回
                          ↓
                    (异步) 工作队列线程 → 加密/解密处理

  优势：
  - 避免阻塞调用线程
  - 利用多核并行处理（通过 cpu 参数分配到不同 CPU）
  - 批量处理提高吞吐量

  类似的异步函数还有 wg_queue_enqueue_per_peer_tx (queueing.h:188) 和 wg_queue_enqueue_per_peer_rx (queueing.h:201)。

> queue_work_on是内核函数吗 

⏺ 是的，queue_work_on 是 Linux 内核提供的工作队列（workqueue）API 函数。

  函数原型：
  bool queue_work_on(int cpu, struct workqueue_struct *wq, struct work_struct *work)

  参数：
  - cpu - 指定在哪个 CPU 上执行工作
  - wq - 工作队列指针
  - work - 要执行的工作项（包含回调函数）

  返回值：
  - true - 工作成功加入队列
  - false - 工作已在队列中（未重复添加）

  功能：
  将一个工作项调度到指定 CPU 的工作队列中异步执行。内核线程会从队列中取出工作项并执行其关联的回调函数。

  相关函数：
  - queue_work() - 不指定 CPU，由系统自动选择
  - schedule_work() - 使用系统默认工作队列
  - queue_delayed_work() - 延迟执行
  - flush_work() - 等待工作完成
  - cancel_work_sync() - 取消工作

  在 WireGuard 中的使用：
  在 queueing.h:184，用于将加密/解密任务分配到特定 CPU 核心上执行：
  queue_work_on(cpu, wq, &per_cpu_ptr(device_queue->worker, cpu)->work);

  这是内核中实现异步任务处理和多核负载均衡的标准机制。

⏺ 好问题！WireGuard 通过状态机制来异步追踪成功或失败，而不依赖直接返回值。关键机制如下：

  1. 数据包状态（State Machine）

  每个数据包在 skb->cb 中携带一个原子状态标志：

  enum packet_state {
      PACKET_STATE_UNCRYPTED,  // 未加密（初始状态）
      PACKET_STATE_CRYPTED,    // 加密成功
      PACKET_STATE_DEAD        // 处理失败
  };

  2. 异步处理流程

  入队时（queueing.h:171）：
  atomic_set_release(&PACKET_CB(skb)->state, PACKET_STATE_UNCRYPTED);

  加密工作线程处理（send.c:491-502）：
  void wg_packet_encrypt_worker(struct work_struct *work) {
      enum packet_state state = PACKET_STATE_CRYPTED;

      if (likely(encrypt_packet(skb, keypair, &simd_context))) {
          // 加密成功，保持 CRYPTED 状态
          wg_reset_packet(skb, true);
      } else {
          // 加密失败，设置为 DEAD
          state = PACKET_STATE_DEAD;
          break;
      }

      // 设置最终状态，通知发送线程
      wg_queue_enqueue_per_peer_tx(first, state);
  }

  发送工作线程检查结果（send.c:443-458）：
  void wg_packet_tx_worker(struct work_struct *work) {
      while ((first = wg_prev_queue_peek(&peer->tx_queue)) != NULL) {
          // 等待状态变为非 UNCRYPTED（阻塞点）
          state = atomic_read_acquire(&PACKET_CB(first)->state);

          if (state == PACKET_STATE_CRYPTED) {
              // 成功：发送数据包
              wg_packet_create_data_done(peer, first);
          } else {
              // 失败：丢弃数据包
              kfree_skb_list(first);
          }
      }
  }

  3. 关键机制

  - 原子操作：atomic_set_release / atomic_read_acquire 保证线程安全
  - 生产者-消费者模型：
    - 加密线程修改状态 → CRYPTED 或 DEAD
    - 发送线程轮询状态 → 根据结果采取行动
  - 入队时立即返回：只检查队列是否满（-ENOSPC / -EPIPE）
  - 处理结果异步通知：通过状态字段传递加密成功/失败信息

  这种设计避免了阻塞，同时通过状态机制实现了可靠的异步结果反馈。

  static void keep_key_fresh(struct wg_peer *peer) {
      rcu_read_lock_bh();
      keypair = rcu_dereference_bh(peer->keypairs.current_keypair);

      // 检查是否需要重新生成密钥
      send = keypair && READ_ONCE(keypair->sending.is_valid) &&
             (atomic64_read(&keypair->sending_counter) > REKEY_AFTER_MESSAGES ||
              (keypair->i_am_the_initiator &&
               wg_birthdate_has_expired(keypair->sending.birthdate, REKEY_AFTER_TIME)));
      rcu_read_unlock_bh();

      if (unlikely(send))
          wg_packet_send_queued_handshake_initiation(peer, false);  // 启动新握手
  }

  安全机制：
  - 前向保密（Perfect Forward Secrecy）：定期更新密钥
  - 防止密钥被破解：限制单个密钥的使用次数和时间

⏺ wg_socket_send_skb_to_peer 函数详解

  函数定位

  不是内核函数，是 WireGuard 自己实现的套接字发送封装函数，位于 socket.c:356。

  ---
  函数原型

  int wg_socket_send_skb_to_peer(struct wg_peer *peer, struct sk_buff *skb, u8 ds)

  ---
  功能说明

  这是 WireGuard 发送数据包的主要入口函数，负责将加密后的数据包通过 UDP
  套接字发送到对等节点。它根据对等节点的地址类型（IPv4/IPv6）选择合适的发送函数。

  ---
  执行流程

  1. 记录数据包长度 (socket.c:358)

  size_t skb_len = skb->len;  // 保存原始长度，用于后续统计

  2. 获取端点读锁 (socket.c:361)

  read_lock_bh(&peer->endpoint_lock);  // 保护端点信息不被并发修改
  - 使用读锁允许多个发送操作并发进行
  - _bh 后缀表示禁用软中断（bottom half）

  3. 地址族判断与发送 (socket.c:364-371)

  if (peer->endpoint.addr.sa_family == AF_INET)       // IPv4
      ret = send4(peer->device, skb, &peer->endpoint, ds,
                  &peer->endpoint_cache);
  else if (peer->endpoint.addr.sa_family == AF_INET6) // IPv6
      ret = send6(peer->device, skb, &peer->endpoint, ds,
                  &peer->endpoint_cache);
  else                                                 // 不支持的地址族
      dev_kfree_skb(skb);  // 直接释放数据包

  关键参数传递：
  - peer->endpoint - 目标地址信息
  - ds - DSCP（Differentiated Services）流量标记
  - &peer->endpoint_cache - 路由缓存，避免重复路由查找

  4. 更新统计信息 (socket.c:374-375)

  if (likely(!ret))
      peer->tx_bytes += skb_len;  // 成功时累计发送字节数

  5. 释放端点锁 (socket.c:377)

  read_unlock_bh(&peer->endpoint_lock);

  ---
  底层调用链

  wg_socket_send_skb_to_peer
      ↓
  ┌───────────────┬────────────────┐
  │   send4()     │    send6()     │  (WireGuard 实现)
  └───────────────┴────────────────┘
      ↓                 ↓
  udp_tunnel_xmit_skb   udp_tunnel6_xmit_skb  (内核函数)
      ↓                 ↓
    UDP 层             UDP 层
      ↓                 ↓
     IP 层             IPv6 层
      ↓                 ↓
    网卡驱动           网卡驱动

  ---
  核心特性

  | 特性     | 说明                         |
  |--------|----------------------------|
  | 地址族自适应 | 自动识别 IPv4/IPv6 并调用对应函数     |
  | 路由缓存优化 | 使用 endpoint_cache 避免重复路由查找 |
  | 并发安全   | 读锁保护端点信息，允许并发发送            |
  | 统计功能   | 成功发送时更新 peer->tx_bytes     |
  | 错误处理   | 发送失败由底层 send4/send6 释放 SKB |

  ---
  send4 和 send6 的核心工作

  IPv4 发送流程 (socket.c:95-189)

  1. 构造流信息 (flowi4)：源/目标 IP、端口、防火墙标记
  2. 路由查找：
    - 优先从缓存获取 (dst_cache_get_ip4)
    - 缓存未命中时调用 ip_route_output_flow
  3. 源地址验证：确保源地址有效，无效时清零重新查找
  4. UDP 封装发送：调用 内核函数 udp_tunnel_xmit_skb

  IPv6 发送流程 (socket.c:231-316)

  - 类似 IPv4，但使用 flowi6 和 ipv6_stub->ipv6_dst_lookup_flow
  - 支持作用域 ID（sin6_scope_id）用于链路本地地址
  - 调用 内核函数 udp_tunnel6_xmit_skb

  ---
  使用场景

  在 wg_packet_create_data_done (send.c:418) 中被调用：

  if (likely(!wg_socket_send_skb_to_peer(peer, skb, PACKET_CB(skb)->ds)
            && !is_keepalive))
      data_sent = true;

  调用时机： 数据包加密完成后，通过 UDP 套接字发送到对等节点。

  ---
  总结

  wg_socket_send_skb_to_peer 是 WireGuard 发送路径的最后一步，它将已加密的数据包交给内核 UDP 隧道函数发送，同时处理 IPv4/IPv6
  双栈、路由缓存和统计等功能。它不是内核函数，而是 WireGuard 对内核 UDP 发送 API 的高层封装。

⏺ send4 返回值对 WireGuard 的意义

  返回值含义

  // socket.c:95-189
  static int send4(...) {
      int ret = 0;  // 默认成功

      // 错误情况 1：套接字不存在
      if (unlikely(!sock)) {
          ret = -ENONET;  // 网络不可达
          goto err;
      }

      // 错误情况 2：路由查找失败
      if (IS_ERR(rt)) {
          ret = PTR_ERR(rt);  // 路由错误码
          goto err;
      }

      // 成功：调用 udp_tunnel_xmit_skb (无返回值检查)
      udp_tunnel_xmit_skb(...);
      goto out;

  err:
      kfree_skb(skb);  // 错误时释放 SKB
  out:
      return ret;
  }

  ---
  返回值类型

  | 返回值           | 含义          | WireGuard 的处理        |
  |---------------|-------------|----------------------|
  | 0             | 成功提交到内核网络栈  | 更新 peer->tx_bytes 统计 |
  | -ENONET       | UDP 套接字不存在  | 不更新统计，数据包已释放         |
  | -ENETUNREACH  | 网络不可达（路由失败） | 不更新统计，数据包已释放         |
  | -EHOSTUNREACH | 主机不可达       | 不更新统计，数据包已释放         |
  | -EINVAL       | 源接口不匹配      | 不更新统计，数据包已释放         |
  | 其他负值          | 各种路由/网络错误   | 不更新统计，数据包已释放         |

  ---
  WireGuard 如何使用返回值

  调用位置 (socket.c:262-287)

  int wg_socket_send_skb_to_peer(struct wg_peer *peer, struct sk_buff *skb, u8 ds)
  {
      size_t skb_len = skb->len;  // ① 提前保存长度
      int ret = -EAFNOSUPPORT;

      read_lock_bh(&peer->endpoint_lock);

      if (peer->endpoint.addr.sa_family == AF_INET)
          ret = send4(...);  // ② 调用 send4
      else if (peer->endpoint.addr.sa_family == AF_INET6)
          ret = send6(...);
      else
          dev_kfree_skb(skb);

      // ③ 关键：只有成功 (ret == 0) 才更新统计
      if (likely(!ret))
          peer->tx_bytes += skb_len;

      read_unlock_bh(&peer->endpoint_lock);
      return ret;  // ④ 返回给调用者
  }

  上层调用 (send.c:418)

  void wg_packet_create_data_done(struct wg_peer *peer, struct sk_buff *first)
  {
      skb_list_walk_safe(first, skb, next) {
          is_keepalive = skb->len == message_data_len(0);

          // ⑤ 检查返回值，决定是否计数
          if (likely(!wg_socket_send_skb_to_peer(peer, skb, PACKET_CB(skb)->ds)
                    && !is_keepalive))
              data_sent = true;  // 成功发送真实数据
      }

      // ⑥ 只有真实数据成功发送才触发定时器
      if (likely(data_sent))
          wg_timers_data_sent(peer);
  }

  ---
  关键设计点

  1. 返回值 ≠ 数据包到达对端

  ret == 0 表示：
    ✅ 数据包已提交到内核 UDP/IP 层
    ✅ 路由查找成功
    ✅ 套接字有效

  ret == 0 不表示：
    ❌ 数据包通过网卡发送成功
    ❌ 数据包到达对端
    ❌ 对端接收成功

  原因： udp_tunnel_xmit_skb 是异步发送，将 SKB 放入网络栈队列后立即返回，不等待实际传输完成。

  2. SKB 所有权转移

  - 成功时 (ret == 0)： SKB 所有权转移给内核网络栈，WireGuard 不再管理
  - 失败时 (ret < 0)： send4 内部已调用 kfree_skb(skb) 释放，WireGuard 无需再处理

  3. 统计意义

  if (likely(!ret))
      peer->tx_bytes += skb_len;  // 累计"尝试发送"的字节数

  peer->tx_bytes 的实际含义：
  - ✅ 成功提交到内核网络栈的字节数
  - ❌ 不是实际通过网卡发送的字节数
  - ❌ 不是对端成功接收的字节数

  ---
  错误场景示例

  场景 1：对端不在线

  send4 返回：0 (成功)
  实际结果：数据包发送到网络，但对端不响应
  WireGuard：更新 tx_bytes，认为发送成功

  场景 2：路由不可达

  send4 返回：-ENETUNREACH
  实际结果：数据包未发送，已释放
  WireGuard：不更新 tx_bytes，日志记录错误

  场景 3：套接字未初始化

  send4 返回：-ENONET
  实际结果：数据包未发送，已释放
  WireGuard：不更新 tx_bytes

  ---
  总结

  | 方面    | 说明                                           |
  |-------|----------------------------------------------|
  | 返回 0  | 数据包成功提交到内核网络栈，开始异步传输                         |
  | 返回负值  | 提交失败，数据包已被 send4 释放                          |
  | 统计更新  | 只有返回 0 时才累计 tx_bytes                         |
  | 真实性   | 返回 0 不保证数据包到达对端                              |
  | 异步性   | udp_tunnel_xmit_skb 不等待实际发送完成                |
  | 定时器触发 | 只有非 Keepalive 包且返回 0 才触发 wg_timers_data_sent |

  核心理解： send4 的返回值只表示"是否成功开始发送流程"，而不是"是否真的发送成功"。这是 Linux 内核异步网络栈的固有特性。

> wg其实是不保证 udp 的成功送达到对端是吗 
  ⎿  ⧉ Selected 1 lines from src/socket.c in Visual Studio Code

⏺ 是的，WireGuard 确实不保证 UDP 数据包成功送达对端。

  这是 WireGuard 基于 UDP 协议的设计特性，而非缺陷。让我详细说明：

  ---
  1. UDP 协议本身的特性

  UDP (User Datagram Protocol) 是无连接、不可靠的传输协议：

  | 特性   | TCP    | UDP (WireGuard 使用) |
  |------|--------|--------------------|
  | 连接建立 | 三次握手   | ❌ 无连接              |
  | 送达保证 | ✅ 保证送达 | ❌ 尽力而为             |
  | 顺序保证 | ✅ 保证顺序 | ❌ 可能乱序             |
  | 丢包重传 | ✅ 自动重传 | ❌ 不重传              |
  | 拥塞控制 | ✅ 有    | ❌ 无                |
  | 性能开销 | 较大     | 很小                 |

  WireGuard 选择 UDP 的原因：
  - 低延迟（无握手、无等待 ACK）
  - 简单高效（无复杂状态机）
  - 适合 VPN 场景（上层协议已有可靠性保证）

  ---
  2. WireGuard 在哪些层面"不保证送达"

  层面 1：发送路径

  // send.c:418
  if (likely(!wg_socket_send_skb_to_peer(peer, skb, PACKET_CB(skb)->ds)
            && !is_keepalive))
      data_sent = true;

  ret == 0 只表示：
  - ✅ 路由查找成功
  - ✅ 数据包提交到内核网络栈队列
  - ❌ 不代表网卡发送成功
  - ❌ 不代表数据包到达对端
  - ❌ 不代表对端处理成功

  层面 2：网络层

  即使 send4 返回成功，数据包仍可能丢失：

  WireGuard → 内核网络栈 → 网卡驱动 → 物理网络 → 对端网卡 → 对端内核 → WireGuard
      ↑              ↓             ↓           ↓          ↓          ↓
   返回0        可能丢弃      可能丢包    网络拥塞    被防火墙拦截  接收队列满

  可能导致丢包的情况：
  1. 本地网卡队列满 - 网卡繁忙时丢弃
  2. 网络拥塞 - 路由器/交换机丢包
  3. NAT 超时 - NAT 映射失效
  4. 防火墙拦截 - 中间设备过滤
  5. 对端接收队列满 - 对端负载过高
  6. 无线信号差 - WiFi 环境丢包

  层面 3：接收确认

  WireGuard 没有发送后的 ACK 确认机制：

  // 发送数据包后，没有代码等待对端回复确认
  wg_socket_send_skb_to_peer(peer, skb, ds);
  // 没有 wait_for_ack() 或类似逻辑

  ---
  3. WireGuard 如何处理不可靠性

  虽然 UDP 本身不可靠，但 WireGuard 通过上层机制提供一定保障：

  (1) 依赖上层协议的可靠性

  WireGuard 只是一个隧道，封装的协议负责可靠性：

  应用数据 (如 HTTP)
      ↓
  TCP 层 (保证可靠传输) ← 这里处理丢包重传
      ↓
  IP 层
      ↓
  WireGuard 加密封装 (UDP)  ← 不保证可靠性
      ↓
  物理网络

  示例：
  - 浏览网页（HTTP over TCP）：TCP 层会重传丢失的包
  - 视频通话（RTP over UDP）：应用层容忍少量丢包
  - SSH（TCP）：TCP 保证命令不丢失

  (2) Keepalive 机制维持连接

  // send.c:361
  void wg_packet_send_keepalive(struct wg_peer *peer)

  作用：
  - 定期发送空数据包（只有 WireGuard 头部）
  - 维持 NAT 映射
  - 探测对端是否在线

  但注意： Keepalive 本身也是 UDP，同样不保证送达。

  (3) 定时器超时检测

  // timers.c
  void wg_timers_data_received(struct wg_peer *peer);

  机制：
  - 长时间未收到对端数据 → 认为连接断开
  - 触发重新握手
  - 但不会重传已丢失的数据包

  (4) 握手重传

  对于握手消息（建立密钥），WireGuard 有重传机制：

  // send.c:114
  void wg_packet_send_queued_handshake_initiation(struct wg_peer *peer, bool is_retry)
  {
      if (!is_retry)
          peer->timer_handshake_attempts = 0;  // 重置重试计数
      // ...
  }

  但对于普通数据包： ❌ 没有重传机制

  ---
  4. 实际案例分析

  案例 1：数据包丢失

  场景：WiFi 信号差，5% 丢包率

  WireGuard 行为：
  1. wg_socket_send_skb_to_peer 返回 0 (成功)
  2. peer->tx_bytes 增加 1000 字节
  3. 数据包在无线网络丢失
  4. WireGuard 不知道丢失，不会重传
  5. 上层 TCP 超时后重传 (如果是 TCP)

  案例 2：对端离线

  场景：对端设备关机

  WireGuard 行为：
  1. 继续发送数据包（返回 0）
  2. 统计继续累计 tx_bytes
  3. 定时器超时后停止发送 Keepalive
  4. 最终触发重新握手（失败）
  5. 用户层协议超时报错

  案例 3：NAT 穿透失败

  场景：NAT 映射失效，数据包被丢弃

  WireGuard 行为：
  1. send4 返回 0（本地路由成功）
  2. 数据包到达 NAT 设备后被丢弃
  3. WireGuard 不知道失败
  4. Keepalive 超时后重新握手

  ---
  5. 为什么这样设计是合理的

  (1) 性能优先

  TCP-based VPN：
    发送 → 等待 ACK → 收到 ACK → 继续发送
    延迟：RTT × 2

  UDP-based VireGuard：
    发送 → 立即继续发送
    延迟：单向传输延迟

  (2) 分层设计原则

  应用层   ← 业务逻辑
    ↓
  传输层   ← 可靠性保证 (TCP)
    ↓
  隧道层   ← WireGuard (高效转发)
    ↓
  网络层   ← IP 路由
    ↓
  链路层   ← 物理传输

  WireGuard 职责：
  - ✅ 加密/解密
  - ✅ 高效转发
  - ❌ 不负责可靠性（交给上层）

  (3) 避免双重重传

  如果 WireGuard 也做重传：

  TCP 重传超时：2 秒
  WireGuard 重传超时：1 秒

  结果：
    1. WireGuard 先重传（浪费带宽）
    2. TCP 再重传（重复浪费）
    3. 拥塞更严重

  ---
  6. 总结

  | 问题               | 答案                  |
  |------------------|---------------------|
  | WireGuard 保证送达吗？ | ❌ 不保证（基于 UDP）       |
  | tx_bytes 统计准确吗？  | ⚠️ 只表示"提交到网络栈"的字节数  |
  | 丢包怎么办？           | 依赖上层协议（TCP）重传       |
  | 如何知道对端是否在线？      | Keepalive 超时 + 握手超时 |
  | 为什么不用 TCP？       | TCP 开销大，延迟高，不适合 VPN |
  | 这是缺陷吗？           | ❌ 这是合理的设计权衡         |

  核心理解：
  // WireGuard 的设计哲学
  ret = send4(...);  // 返回 0 = "我尽力了"
  if (!ret)
      tx_bytes++;    // "我认为发送成功了"

  // 但实际情况可能是：
  // - 数据包在网络中丢失
  // - 对端已离线
  // - NAT 映射失效

  // 这些问题由上层协议 (TCP/应用层) 处理

  这就是为什么 WireGuard 能做到高性能、低延迟的原因 —— 
  它把可靠性保证交给了最适合处理它的层（传输层/应用层），而不是在隧道层做重复的工作。

  ┌─────────────────────────────────────────────────┐
  │ WireGuard 头部                                  │
  │ - type: MESSAGE_DATA (4)                       │
  │ - key_idx: 0x12AB34CD                          │
  │ - counter: 42                                  │
  └─────────────────────────────────────────────────┘
  │ 加密负载 (ChaCha20Poly1305 加密)                │
  │ 原始内容 (明文状态)：                            │
  │   ┌───────────────────────────────────────┐    │
  │   │ IP: 10.0.0.2 → 8.8.8.8               │    │
  │   │ UDP: 54321 → 53                      │    │
  │   │ DNS: "google.com" A?                 │    │
  │   └───────────────────────────────────────┘    │
  │ + Poly1305 认证标签 (16 字节)                   │
  └─────────────────────────────────────────────────┘

  (4) 外层 UDP 封装

  ┌───────────────────────────────────────────────┐
  │ 外层 IP 头                                     │
  │ - 源: 1.2.3.4 (本机公网 IP)                    │
  │ - 目标: 5.6.7.8 (对端公网 IP)                  │
  │ - 协议: UDP (17)                              │
  └───────────────────────────────────────────────┘
  ┌───────────────────────────────────────────────┐
  │ 外层 UDP 头                                    │
  │ - 源端口: 51820 (WireGuard 端口)               │
  │ - 目标端口: 51820                              │
  └───────────────────────────────────────────────┘
  ┌───────────────────────────────────────────────┐
  │ WireGuard 数据包 (已加密)                      │
  └───────────────────────────────────────────────┘

  ---
  4. 为什么要 UDP 套 UDP？

  (1) 穿透 NAT/防火墙

  服务器 A (NAT 后)       互联网        服务器 B
      │                    │                │
      │ 外层 UDP:51820     │                │
      ├───────────────────→│                │
      │                    ├───────────────→│
      │                    │   NAT 转换     │

  如果不用外层 UDP：
  - 加密数据直接放在 IP 层 → NAT 无法正确处理
  - 防火墙可能拦截非标准协议

  (2) 利用 UDP 的无状态特性

  // 外层 UDP 的优势：
  - 无连接建立开销
  - 快速恢复 (对端 IP 变化时)
  - 低延迟

  (3) 兼容现有网络基础设施

  路由器/交换机/防火墙都支持 UDP
  → WireGuard 数据包被当作普通 UDP 处理
  → 避免特殊协议支持问题

  ---
  5. 开销分析

  头部开销：

  原始 DNS 查询：
    UDP 头: 8 字节
    DNS 数据: ~40 字节
    总计: 48 字节

  经过 WireGuard：
    外层 IP 头: 20 字节 (IPv4) 或 40 字节 (IPv6)
    外层 UDP 头: 8 字节
    WireGuard 头: 16 字节
    Poly1305 标签: 16 字节
    内层数据: 48 字节 (加密)
    填充: ~0-16 字节
    总计: ~108-124 字节

  开销: +60-76 字节 (约 125-158%)

  性能影响：

  // 优势：
  ✅ 加密只做一次 (ChaCha20Poly1305 非常快)
  ✅ 无额外 TCP 握手
  ✅ 无重传机制的延迟

  // 劣势：
  ❌ 每个包增加 ~60 字节开销
  ❌ MTU 需要减小 (避免分片)

  ---
  6. 与其他 VPN 的对比

  | VPN 类型        | 封装方式      | 性能          |
  |---------------|-----------|-------------|
  | WireGuard     | UDP 套 UDP | ⭐⭐⭐⭐⭐ 最快    |
  | OpenVPN (UDP) | UDP 套 UDP | ⭐⭐⭐ 中等      |
  | OpenVPN (TCP) | TCP 套 TCP | ⭐⭐ 慢 (双重重传) |
  | IPsec         | IP 层封装    | ⭐⭐⭐⭐ 快但复杂   |
  | PPTP          | GRE 封装    | ⭐⭐⭐⭐ 快但不安全  |

  8. 总结

  | 问题                      | 答案                         |
  |-------------------------|----------------------------|
  | WireGuard 会再包装一层 UDP 吗？ | ✅ 是的，外层 UDP 端口 51820       |
  | 相当于 UDP 套 UDP？          | ✅ 完全正确                     |
  | 为什么要这样？                 | 穿透 NAT、防火墙友好、低延迟           |
  | 开销大吗？                   | ~60-76 字节额外头部，但性能仍很好       |
  | 内层 UDP 加密了吗？            | ✅ 完全加密（ChaCha20Poly1305）   |
  | 中间设备能看到内层 UDP 吗？        | ❌ 只能看到外层 UDP (51820→51820) |

  核心理解：
  用户 UDP 包 (明文)
      ↓ 加密
  WireGuard 包 (密文)
      ↓ UDP 封装
  外层 UDP 包 (端口 51820)
      ↓ IP 封装
  物理网络发送

  中间设备只能看到：
  "某人在用 UDP 51820 端口传输数据"
  但完全不知道内层是什么协议 (TCP? UDP? ICMP?)

  这就是 WireGuard 的"隧道"本质 —— 在 UDP 隧道里传输加密的 IP 包！

  ---
  1. 函数签名与职责

  // socket.c:95
  static int send4(struct wg_device *wg, struct sk_buff *skb,
                   struct endpoint *endpoint, u8 ds, struct dst_cache *cache)

  用人话说：
  "把一个已经加密好的 WireGuard 数据包，通过 IPv4 网络，用 UDP 协议发送给对端。"

  参数含义：
  - wg - WireGuard 设备（就像你的 wg0 接口）
  - skb - 数据包（已加密的 WireGuard 数据）
  - endpoint - 对端信息（对方的 IP 地址、端口）
  - ds - DSCP 流量标记（QoS 用，一般是 0）

  ---
  3. 逐步详细解析

  步骤 1：构造流信息 (flowi4)

  struct flowi4 fl = {
      .saddr = endpoint->src4.s_addr,             // 源 IP
      .daddr = endpoint->addr4.sin_addr.s_addr,   // 目标 IP
      .fl4_dport = endpoint->addr4.sin_port,      // 目标端口
      .flowi4_mark = wg->fwmark,                  // 防火墙标记
      .flowi4_proto = IPPROTO_UDP                 // 协议: UDP
  };

  什么是 flowi4？
  这是内核路由查找的"查询表单"，告诉路由系统："我要发送一个包到哪里，用什么协议。"

  实际例子：
  假设：
    本机 IP: 1.2.3.4
    对端 IP: 5.6.7.8:51820
    防火墙标记: 0xca6c (用于策略路由)

  构造的 flowi4：
    .saddr = 1.2.3.4        (本机)
    .daddr = 5.6.7.8        (对端)
    .fl4_dport = 51820      (WireGuard 端口)
    .flowi4_mark = 0xca6c   (路由标记)
    .flowi4_proto = UDP

  ---
  步骤 2：设置数据包属性

  skb_mark_not_on_list(skb);   // 标记数据包不在链表中
  skb->dev = wg->dev;          // 设置发送设备 (wg0)
  skb->mark = wg->fwmark;      // 设置防火墙标记

  为什么要设置这些？

  1. skb_mark_not_on_list
  // 告诉内核："这个包是独立的，不在任何队列链表中"
  // 避免内核误以为它在某个队列里，导致内存管理错误
  2. skb->dev = wg->dev
  // 记录这个包来自哪个设备
  // 统计和调试时有用
  3. skb->mark = wg->fwmark
  // 防火墙标记 (用于策略路由)
  // 例如：ip rule add fwmark 0xca6c table 100
  //       让打了这个标记的包走特定路由表

  实际场景：
  # 配置防火墙标记路由
  wg set wg0 fwmark 51820

  # 内核处理流程：
  数据包.mark = 51820
    ↓
  查路由表：fwmark 51820 → table 200
    ↓
  使用特定路由 (例如通过 eth1 发送)

  ---
  步骤 3：获取 UDP 套接字

  rcu_read_lock_bh();                      // 进入 RCU 读临界区
  sock = rcu_dereference_bh(wg->sock4);    // 获取 IPv4 套接字

  if (unlikely(!sock)) {                   // 套接字不存在
      ret = -ENONET;                       // 网络不可达
      goto err;
  }

  fl.fl4_sport = inet_sk(sock)->inet_sport; // 获取源端口 (通常 51820)

  什么是 RCU？
  RCU (Read-Copy-Update) 是内核的无锁并发机制。
  - 读者不加锁，可以并发访问
  - 写者更新时复制，确保读者不受影响

  为什么用 RCU？
  // 发送路径是高频操作 (每秒几千次)
  // 如果用普通锁：
  mutex_lock(&wg->sock_lock);    // ← 所有 CPU 串行等待
  sock = wg->sock4;
  mutex_unlock(&wg->sock_lock);

  // 用 RCU：
  rcu_read_lock_bh();            // ← 无锁，多 CPU 并发读取
  sock = rcu_dereference_bh(wg->sock4);
  // ... 使用 sock ...
  rcu_read_unlock_bh();

  源端口从哪来？
  fl.fl4_sport = inet_sk(sock)->inet_sport;

  // 通常在套接字初始化时绑定：
  // socket.c:922
  ret = udp_sock_create(net, &port4, &new4);
  // port4.local_udp_port = htons(51820);

  // 所以 fl.fl4_sport = 51820

  ---
  步骤 4：路由查找 (核心逻辑)

  这是 send4 最复杂的部分，分为 4 个子步骤：

  4.1 尝试从缓存获取路由

  if (cache)
      rt = dst_cache_get_ip4(cache, &fl.saddr);

  为什么要缓存？
  路由查找很慢 (查路由表、策略路由、ARP 等)
  典型延迟：5-20 微秒

  如果每个包都查：
    1000 包/秒 × 10 微秒 = 10 毫秒 CPU 时间/秒

  用缓存：
    命中率 99% → 查询次数降低 100 倍
    1000 包/秒 × 0.1 微秒 = 0.1 毫秒 CPU 时间/秒

  缓存命中示例：
  // 第一个包：缓存未命中
  rt = NULL;  // 缓存返回 NULL
  // ... 查找路由表 ...
  dst_cache_set_ip4(cache, &rt->dst, fl.saddr); // 存入缓存

  // 第二个包到第 1000 个包：缓存命中
  rt = dst_cache_get_ip4(cache, &fl.saddr);  // 直接返回路由
  // 跳过路由查找，直接发送

  4.2 缓存未命中，进行安全检查

  if (!rt) {  // 缓存未命中
      security_sk_classify_flow(sock, flowi4_to_flowi(&fl));
      // ↑ SELinux/AppArmor 安全策略检查

  什么是安全策略分类？
  // SELinux 示例规则：
  // "标记为 wireguard_t 的进程，只能访问 vpn_peer_t 类型的地址"

  security_sk_classify_flow() 会检查：
  1. 套接字的安全上下文 (wireguard_t)
  2. 目标地址的安全标签 (vpn_peer_t)
  3. 是否允许通信

  如果违反策略 → 数据包被阻止

  4.3 验证源地址

  if (unlikely(!inet_confirm_addr(sock_net(sock), NULL, 0,
                                  fl.saddr, RT_SCOPE_HOST))) {
      // 源地址无效，清除
      endpoint->src4.s_addr = 0;
      endpoint->src_if4 = 0;
      fl.saddr = 0;
      if (cache)
          dst_cache_reset(cache);  // 重置缓存
  }

  为什么要验证源地址？

  场景 1：网卡被禁用
  # 之前配置的源地址
  endpoint->src4 = 192.168.1.100

  # 网卡被禁用
  sudo ip link set eth0 down

  # 源地址验证失败
  inet_confirm_addr() → false

  # 清除无效源地址
  endpoint->src4 = 0.0.0.0
  fl.saddr = 0  # 让内核自动选择源地址

  场景 2：IP 地址变更
  # DHCP 租约到期，获取新 IP
  旧 IP: 192.168.1.100 → 新 IP: 192.168.1.200

  # 缓存中的旧源地址失效
  inet_confirm_addr(192.168.1.100) → false

  # 清零后重新查找
  fl.saddr = 0
  内核选择新的源地址 192.168.1.200

  4.4 查找路由

  rt = ip_route_output_flow(sock_net(sock), &fl, sock);

  内核路由查找过程：

  1. 策略路由 (ip rule)
     ├─ 检查 fwmark
     ├─ 检查源/目标地址
     └─ 选择路由表

  2. 路由表查找 (ip route)
     ├─ 最长前缀匹配
     ├─ 查找网关
     └─ 确定出口接口

  3. ARP/邻居发现
     ├─ 查 ARP 缓存
     └─ 必要时发 ARP 请求

  4. 返回路由结果
     └─ rtable 结构体

  实际例子：

  # 路由配置
  ip route show
  default via 192.168.1.1 dev eth0
  10.0.0.0/24 dev wg0

  # 查找 5.6.7.8 的路由
  ip_route_output_flow(5.6.7.8)
    ↓
  匹配 default 路由
    ↓
  返回：
    rt->dst.dev = eth0
    rt->rt_gateway = 192.168.1.1
    rt->rt_src = 192.168.1.100 (本机 IP)

  4.5 验证源接口

  if (unlikely(endpoint->src_if4 &&
               ((IS_ERR(rt) && PTR_ERR(rt) == -EINVAL) ||
                (!IS_ERR(rt) && rt->dst.dev->ifindex != endpoint->src_if4)))) {
      // 接口不匹配，重新查找
      endpoint->src4.s_addr = 0;
      endpoint->src_if4 = 0;
      fl.saddr = 0;
      if (cache)
          dst_cache_reset(cache);
      if (!IS_ERR(rt))
          ip_rt_put(rt);
      rt = ip_route_output_flow(sock_net(sock), &fl, sock);
  }

  为什么要验证接口？

  场景：多网卡环境
  # 系统有两个网卡
  eth0: 192.168.1.100 (家庭网络)
  eth1: 10.0.0.1 (公司 VPN)

  # 之前通过 eth1 通信
  endpoint->src_if4 = 3  (eth1 的 ifindex)

  # eth1 断开，路由切换到 eth0
  rt->dst.dev->ifindex = 2  (eth0)

  # 检测到不匹配
  2 != 3 → 接口变化

  # 清除缓存，重新查找
  endpoint->src_if4 = 0
  // 重新查找后使用 eth0

  4.6 路由查找失败处理

  if (IS_ERR(rt)) {
      ret = PTR_ERR(rt);
      net_dbg_ratelimited("%s: No route to %pISpfsc, error %d\n",
                          wg->dev->name, &endpoint->addr, ret);
      goto err;
  }

  常见错误码：

  | 错误码           | 含义    | 触发场景        |
  |---------------|-------|-------------|
  | -ENETUNREACH  | 网络不可达 | 无路由到目标网络    |
  | -EHOSTUNREACH | 主机不可达 | 有路由但 ARP 失败 |
  | -EINVAL       | 无效参数  | 源地址无效       |
  | -EACCES       | 权限拒绝  | 防火墙拦截       |

  日志示例：
  [WireGuard] wg0: No route to 5.6.7.8:51820, error -101
                                      ↑ ENETUNREACH

  4.7 缓存路由结果

  if (cache)
      dst_cache_set_ip4(cache, &rt->dst, fl.saddr);

  缓存内容：
  struct dst_cache {
      struct dst_entry *dst;  // 路由表项
      __be32 saddr;           // 源地址
      int ifindex;            // 出口接口
      // ...
  };

  // 下次查找时直接返回，无需重新查路由表

  ---
  步骤 5：UDP 隧道发送

  skb->ignore_df = 1;  // 忽略 Don't Fragment 标志

  udp_tunnel_xmit_skb(
      rt,                          // 路由表项
      sock,                        // UDP 套接字
      skb,                         // 数据包
      fl.saddr,                    // 源 IP
      fl.daddr,                    // 目标 IP
      ds,                          // DSCP (通常是 0)
      ip4_dst_hoplimit(&rt->dst),  // TTL (通常是 64)
      0,                           // Don't Fragment = 0
      fl.fl4_sport,                // 源端口 (51820)
      fl.fl4_dport,                // 目标端口 (51820)
      false,                       // xnet (跨网络命名空间)
      false                        // nocheck (UDP 校验和)
  );

  udp_tunnel_xmit_skb 做什么？

  1. 添加 UDP 头部
  struct udphdr *uh = (struct udphdr *)skb_push(skb, sizeof(*uh));
  uh->source = htons(fl.fl4_sport);  // 51820
  uh->dest = htons(fl.fl4_dport);    // 51820
  uh->len = htons(skb->len);
  uh->check = 0;  // 校验和稍后计算
  2. 添加 IP 头部
  struct iphdr *iph = (struct iphdr *)skb_push(skb, sizeof(*iph));
  iph->version = 4;
  iph->ihl = 5;
  iph->tos = ds;  // DSCP
  iph->tot_len = htons(skb->len);
  iph->id = 0;
  iph->frag_off = 0;  // DF = 0
  iph->ttl = ip4_dst_hoplimit(&rt->dst);  // 64
  iph->protocol = IPPROTO_UDP;
  iph->saddr = fl.saddr;  // 1.2.3.4
  iph->daddr = fl.daddr;  // 5.6.7.8
  3. 计算校验和
  iph->check = ip_fast_csum((u8 *)iph, iph->ihl);
  4. 提交到网络设备队列
  dev_queue_xmit(skb);  // 交给网卡驱动

  最终数据包结构：
  ┌───────────────────┬───────────────────┬──────────────────┬─────────────┐
  │ IP 头 (20 字节)   │ UDP 头 (8 字节)   │ WireGuard 头     │ 加密数据    │
  ├───────────────────┼───────────────────┼──────────────────┼─────────────┤
  │ src: 1.2.3.4     │ sport: 51820      │ type: 4          │ (ChaCha20   │
  │ dst: 5.6.7.8     │ dport: 51820      │ key_idx: 12345   │  加密)      │
  │ proto: UDP       │ len: 124          │ counter: 678     │             │
  │ ttl: 64          │ checksum: 0x1234  │                  │ + Poly1305  │

  步骤 6：错误处理与返回

  goto out;  // 成功跳转到 out 标签

  err:
      kfree_skb(skb);  // 错误时释放数据包
  out:
      rcu_read_unlock_bh();  // 释放 RCU 锁
      return ret;  // 返回结果 (0 或负数)

  返回值处理：
  // 调用者 (wg_socket_send_skb_to_peer)
  ret = send4(...);

  if (likely(!ret))
      peer->tx_bytes += skb_len;  // 成功：更新统计
  else
      // 失败：数据包已被 send4 释放，无需再处理

  4. 完整调用示例

  场景：发送加密的 DNS 查询

  // 1. 加密完成，准备发送
  struct sk_buff *skb;  // 包含加密的 DNS 查询
  struct wg_peer *peer; // 对端信息

  // 2. 调用 send4
  int ret = send4(
      peer->device,           // wg0 设备
      skb,                    // 加密数据包
      &peer->endpoint,        // 对端 5.6.7.8:51820
      PACKET_CB(skb)->ds,     // DSCP = 0
      &peer->endpoint_cache   // 路由缓存
  );

  // 3. 内部流程
  send4:
    ├─ 构造 flowi4 {1.2.3.4 → 5.6.7.8:51820}
    ├─ 获取套接字 (sock4)
    ├─ 查路由缓存 → 命中
    ├─ 调用 udp_tunnel_xmit_skb
    │   ├─ 添加 UDP 头 (51820 → 51820)
    │   ├─ 添加 IP 头 (1.2.3.4 → 5.6.7.8)
    │   └─ 提交到 eth0 网卡队列
    └─ 返回 0

  // 4. 返回后
  if (!ret)
      peer->tx_bytes += skb->len;  // 统计+148 字节

  5. 性能优化细节

  (1) RCU 无锁读取

  rcu_read_lock_bh();
  sock = rcu_dereference_bh(wg->sock4);
  // 多 CPU 并发发送，无锁竞争

  (2) 路由缓存

  rt = dst_cache_get_ip4(cache, &fl.saddr);
  // 命中率 99%+，节省 90% 路由查找时间

  (3) likely/unlikely 提示

  if (unlikely(!sock))  // 告诉编译器这是冷路径
      goto err;

  if (likely(!ret))  // 告诉编译器这是热路径
      peer->tx_bytes += skb_len;

  编译器优化：
  ; 热路径 (likely) - 代码紧凑，减少跳转
  test eax, eax
  jz   success_path   ; 顺序执行

  ; 冷路径 (unlikely) - 代码远离，分支预测优化
  jmp  error_handler  ; 远跳转

  6. 常见问题

  Q1: 为什么 udp_tunnel_xmit_skb 没有检查返回值？

  A: 该函数设计为"fire and forget"，成功提交到网络栈后立即返回，不等待发送完成。失败时会自动释放 SKB。

  Q2: ignore_df = 1 是什么意思？

  A:
  skb->ignore_df = 1;  // 允许分片，即使 DF=1
  WireGuard 数据包可能较大，需要分片才能通过某些网络。

  Q3: 路由缓存什么时候失效？

  A:
  // 手动重置
  dst_cache_reset(cache);

  // 自动失效场景：
  - 网卡状态变化 (up/down)
  - 路由表更新
  - 源地址变化
  - 接口切换

  7. 总结

  | 阶段        | 关键操作       | 耗时            | 失败率    |
  |-----------|------------|---------------|--------|
  | 1. 构造流信息  | 填充结构体      | ~10 ns        | 0%     |
  | 2. 设置属性   | 标记字段       | ~20 ns        | 0%     |
  | 3. 获取套接字  | RCU 读取     | ~30 ns        | <0.01% |
  | 4. 路由查找   | 缓存命中/路由表查找 | 50 ns - 10 μs | <1%    |
  | 5. UDP 发送 | 封装+提交      | ~200 ns       | <0.1%  |
  | 6. 返回     | 清理资源       | ~10 ns        | 0%     |

  核心理解：
  send4 = 路由查找器 + UDP 封装器

  输入：加密的 WireGuard 数据包
  输出：外层 UDP/IP 封装完成，提交到网卡队列

  性能关键：路由缓存命中率
  可靠性：依赖上层协议 (TCP) 重传

  send4 就像一个"快递打包员" —— 拿到加密包裹，贴上快递单（UDP/IP
  头），扔进快递车（网卡队列），然后就不管了。包裹能否送到，那是快递公司（网络栈）和收件人（上层协议）的事！
